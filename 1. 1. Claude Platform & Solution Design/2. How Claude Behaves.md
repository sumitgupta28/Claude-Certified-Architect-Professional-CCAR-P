### 1. Summary

The [Claude Platform & Solution Design](https://anthropic-partners.skilljar.com/path/claude-certified-architect-professional/claude-platform-solution-design/486647/scorm/2gvs1pi0tq0sq) module outlines the **four core properties** of Claude that enterprise architects must design around as structural materials rather than flaws: **Next-token prediction**, **Knowledge**, **Working memory**, and **Steerability**.

* **Next-token prediction & Non-determinism:** Claude excels at pattern recognition (summarizing, reformatting) but carries hallucination risks for precise facts (names, dates, statistics). Because identical inputs can yield variable outputs across runs, architects must deploy **evaluation frameworks**, **generator-verifier loops**, and **uncertainty signaling**.
* **Knowledge & Capability Boundaries:** Model reliability is high for common, static concepts in training data but low for rare, private, or fast-changing domain knowledge. External systems integrated via **Model Context Protocol (MCP)**, **Retrieval-Augmented Generation (RAG)**, or **tool calls** must serve as the authoritative source of truth.
* **Working Memory & Context Limits:** The **context window** imposes a hard token budget where context ordering, inclusion, and pruning directly dictate cost, latency, and reasoning capability.
* **Steerability & Confidence vs. Validity:** Claude generates incorrect responses with the same fluent, assured tone used for correct ones. Ensuring system integrity requires embedding **human-in-the-loop (HITL)** controls and validation layers into production workflows.

### 2. Clear & Simple Explanation

* **Four Model Behaviors:** Just as civil engineers design around the physical properties of concrete and steel, software architects design around how Claude inherently processes text.
* **Non-Determinism:** Passing the exact same prompt twice can generate slightly different outputs. A successful demo run does not prove production readiness; continuous evaluation is mandatory.
* **Confidence Is Not Validity:** Flawless grammar and an authoritative tone do not guarantee factual correctness. Never assume fluent phrasing equals an accurate execution path.
* **Knowledge Boundaries:** Claude understands general public knowledge well, but enterprise-specific or live real-time facts must be provided externally via search or database tools.
* **Context Budgeting:** The model's context window is finite memory space. Every token included adds latency and cost, making context selection an explicit architectural choice.

### 3. Preserve Technical Accuracy

Architectural design requires mapping each model property directly to technical mitigations and design consequences:

* **Next-token prediction:** Mitigated via **generator-verifier loops**, **uncertainty signaling**, and automated **evaluation frameworks** to detect non-deterministic output drift across production deployments.
* **Knowledge and capability boundaries:** Addressed by establishing external sources of truth through **Model Context Protocol (MCP)** server integration, **Retrieval-Augmented Generation (RAG)** pipelines, and authoritative **tool calls**.
* **Working memory constraints:** Managed through token budget optimization, payload pruning, and structured context hierarchy within the strict limits of the **context window**.
* **Steerability limits:** Mitigated by placing **human-in-the-loop (HITL)** decision gates and validation layers at critical operational boundaries to counteract fluent unvalidity.

### 4. Real-World Application

An automated claims processing platform at a health insurance provider utilizes Claude to extract details from medical bills and policy documents:

* **Knowledge & Retrieval:** Because policy coverage rules change quarterly and contain proprietary terms, the system routes claims data through **MCP tools** and **RAG pipelines**, treating internal relational databases as the sole source of truth rather than relying on model pre-training.
* **Non-Determinism & Generator-Verifier Loop:** To handle non-deterministic extraction variances, the pipeline uses a primary model to extract structured JSON data, followed by a **generator-verifier loop** where a secondary validation prompt checks line-item sums against raw bill amounts.
* **Human-in-the-Loop Placement:** Recognizing that **confidence is not validity**, any payout decision exceeding $5,000 or exhibiting low certainty scores is flagged with **uncertainty signaling** and automatically routed to a human adjuster for review before authorization.

**Question 1**

An enterprise architect runs a pilot demo of an AI financial auditor. Five consecutive test runs yield identical, correct output categories. Based on this result, the team deploys the service to production without automated evaluation checks. In week two, output categorization drifts on identical input statements. What fundamental design error occurred?

A) The team failed to increase the context window token budget prior to launch.

B) The architect mistook successful demo executions for system determinism and neglected to implement an evaluation framework and verification loop.

C) The model's MCP server lost connection to the underlying vector database.

D) The system prompt failed to leverage XML tags to enforce strict JSON parsing rules.

**Question 2**

A developer wants Claude to verify real-time inventory counts across distributed warehouses. The developer hardcodes static inventory snapshots into the system prompt. During peak sales, order allocations fail because inventory levels change rapidly. Which architectural property was misapplied, and what is the proper mitigation?

A) Steerability was misapplied; mitigate by increasing system prompt temperature.

B) Next-token prediction was misapplied; mitigate by enabling prefix caching.

C) Knowledge boundaries were misapplied; mitigate by making external warehouse APIs the source of truth via tool calls or MCP.

D) Working memory was misapplied; mitigate by expanding the context window budget.

**Question 3**

A customer support agent powered by Claude provides a plausible, highly articulate explanation of a refund policy that does not exist in company documentation. What property of LLMs explains this behavior, and what architectural safeguard should be implemented?

A) Next-token prediction drift; mitigate by switching to a lower-cost model tier.

B) Working memory exhaustion; mitigate by clearing user session histories.

C) Confidence does not equal validity; mitigate by implementing generator-verifier loops, source citations, and human-in-the-loop review for policy outputs.

D) Non-determinism; mitigate by running the request across three parallel agents and picking the shortest completion.

#### Answer & Explanation Key

* **Question 1 Correct Answer:** **B**
*Explanation:* The CCAR-P framework emphasizes that LLMs are non-deterministic systems. A small number of clean demo runs is not proof of determinism; production architectures must include evaluation frameworks and verification checks to monitor and manage output drift.
* **Question 2 Correct Answer:** **C**
*Explanation:* Fast-changing, private, or real-time data falls outside the model's static knowledge boundaries. Real-time data must be fetched dynamically using tool calls, RAG, or MCP servers to ensure external systems remain the source of truth.
* **Question 3 Correct Answer:** **C**
*Explanation:* Fluency and confident tone do not guarantee validity. Mitigations include generator-verifier loops, mandating grounding citations, and placing human-in-the-loop review gates on high-risk policy outputs.

### Key Technical Terms

* **Next-token Prediction:** The fundamental probabilistic mechanism by which Claude generates text sequentially, enabling pattern matching while creating risk for factual hallucinations.
* **Non-determinism:** The property where identical inputs can yield different completion outputs across separate execution runs.
* **Knowledge Boundary:** The operational threshold separating static, public training data from rare, private, or real-time information requiring external sources of truth.
* **Working Memory:** The active processing space governed by the model's finite context window token budget.
* **Generator-Verifier Loop:** An architectural pattern where one LLM step generates an output and a subsequent validation step evaluates or checks that output for correctness before approval.
* **Model Context Protocol (MCP):** An open standard for securely connecting LLM applications to external databases, tools, and content repositories.
* **Uncertainty Signaling:** Prompting or architectural techniques that instruct the model to explicitly indicate low confidence or missing context rather than inventing answers.
* **Human-in-the-Loop (HITL):** The practice of placing human validation checkpoints at high-risk decision points to review model outputs before execution.
